# Examples

Run these scripts from a source checkout after installing the package. Each
script defines its own inputs or loads the small files in `examples/data/`.

| Example | Command | Requirements |
| --- | --- | --- |
| Generate a rationale and select return-policy evidence | `python examples/return_policy.py` | `hf` and `sentence-transformers` extras and model weights |
| Select chunks from supplied rationales | `python examples/minimal_selection.py` | Base package |
| Preserve document objects in a reranker pipeline | `python examples/reranker_replacement.py` | Base package |
| Prepare DPO preference splits | `python examples/dpo_preparation.py` | Base package |
| Generate rationales with a language model | `python examples/generate_rationales.py "Does the agreement allow termination for non-payment?"` | `hf` extra and model weights |
| Verify evidence with a chat model | `python examples/verify_evidence.py --model Qwen/Qwen2.5-0.5B-Instruct` | `hf` extra and model weights |

The base examples use `HashingEncoder`, which demonstrates the API using shared
words. They supply their rationales explicitly and do not call a language model.
For semantic matching, use `SentenceTransformerEncoder` with the
`sentence-transformers` extra.

The return-policy walkthrough uses `Qwen/Qwen2.5-0.5B-Instruct` with chat
formatting. The standalone `generate_rationales.py` example defaults to
`TinyLlama/TinyLlama-1.1B-Chat-v1.0`.
Verification requires an explicit `--model`; the command above uses a compact
chat model to demonstrate the request/response interface. These example models
are not benchmarked verifier recommendations: valid JSON can still contain an
incorrect decision. Choose a checkpoint evaluated for your application.
Use `--device` to select a device explicitly. Their responses
are generated by the model, not hardcoded decisions. A small model can return
invalid verifier JSON; such chunks are rejected with `PARSE_ERROR` by default.

The files in `data/` are synthetic examples of contract language and preference
annotations. They illustrate input formats; research benchmark data and trained
checkpoints must be obtained separately. The three preference pairs are
suitable for demonstrating preparation, not assessing training quality.
